# Syngine Documentation
# Concept: Rendering - Shaders & Uniforms
[<-- Back](../index.md)

Syngine's Standard Render Pipeline (SRP) is built to be primarily data-driven. The system uses a strict separation of powers to make it easy to extend data to both new engine and user-generated content.

You may be looking for: [All Engine Uniform Providers](#engine-uniform-providers) or [Documenting Shaders](#documenting-shaders)

## Shaders
Shaders in Syngine are stateless definitions of GPU programs. They own their uniform handle(s).

Shaders rely on an XML metadata file in the shader bundle to define what uniforms they expect, their data type, their frequency, and how they map to memory. This XML file is generated by the build system using `syntools` before shader compilation.

Shaders may define uniforms, material parameters, engine samplers, and texture samplers using comments in the shader source. Uniforms and Engine Samplers require a source from the engine. Samplers require a stage to be specified. Uniforms and mat params will have their type deduced from the uniform.

Uniform types:
- `SAMPLER`
- `VEC4`
- `MAT3`
- `MAT4`

Uniform frequencies:
- `FRAME` - Global state variables (Time, wind, etc). Updated once per frame.
- `VIEW` - Camera state (View projection). Updated once per active view.
- `DRAW` - Object state (Transforms, material parameters, samplers). Updated per object.

## Uniforms
Uniforms are data passed to the GPU from the CPU. Here, we strictly define a Uniform as a constant, rather than including texture samplers and material parameters (See [Materials](./materials.md)).

### The Uniform Registry
The registry bridges together gameplay logic and the renderer without physically coupling them in code. It uses type erased function pointers to supply data to the GPU on demand. These function pointers are provided the `RenderPacket` as a `context` argument, which is only provided during DRAW uniforms. The context should be cast back to its type using `const T& data = UniformRegistry::GetContext<const T*>(context)`

### Uniform Data Providers
Uniform Data Providers are the earlier mentioned function pointers used to provide GPU bound data. Shaders ask for one of these providers when defining a uniform. These functions should be as simple and flat as possible as they are called during the render process. An example of a UDP could be:
```cpp
UniformRegistry::RegisterProvider(
    "Camera.ViewProjection",
    UniformDataProvider{
        .type = UniformType::MAT4,
        .frequency = UniformFrequency::VIEW,
        .num = 1,
        .getter = [](const void* rawPacket) -> const void* {
            return Renderer::GetActiveCamera()->GetViewProjMatrix().data();
        }
    }
);
```
Or
```cpp
UniformRegistry::RegisterProvider(
    "Billboard.Position",
    UniformDataProvider{
        .type = UniformType::VEC4,
        .frequency = UniformFrequency::DRAW,
        .num = 1,
        .getter = [](const void* rawPacket) -> const void* {
            const RenderPacket& packet = UniformRegistry::GetContext<const RenderPacket>(rawPacket);
            TransformComponent transform = packet.go->GetComponent<TransformComponent>();

            thread_local Math::Vec4 data;
            data = { transform->GetWorldPosition(), 0.0f };

            return data.data();
        }
    }
);
```

## Documenting Shaders
Shaders are documented in the source file using special annotation comments that the metadata generator reads. These comments are parsed from the shader source and turned into the XML metadata used by the engine.

### Supported comment format
Use a single-line comment that begins with `// @` followed by a supported tag. The annotation must appear immediately above the declaration it describes.

Supported tags:
- `@EngineUniform` for engine-provided uniforms
- `@EngineSampler` for engine-provided samplers
- `@MaterialParam` or `@MaterialParameter` for material parameters
- `@Sampler` for texture samplers

Supported attributes on the annotation line:
- `name="..."` to explicitly name the entry
- `freq="..."` for uniforms, such as `draw`, `frame`, or `view`
- `src="..."` for engine-backed uniforms or samplers
- `default="..."` for an optional default value
- `num="..."` for array-like uniforms or parameters
- `stage="..."` for samplers, such as `0`, `1`, or `3`

The parser reads the annotation line, then looks at the next line for the declaration. That declaration must be a real shader declaration such as `uniform vec4 u_lightDir;` or `SAMPLER2D(s_albedo, 0);`.

### Examples
```bgsl
// @EngineUniform freq="draw" src="Renderer.SunDirection"
uniform vec4 u_lightDir;
```

```bgsl
// @Sampler name="s_albedo" stage="0"
SAMPLER2D(s_albedo, 0);
```

```bgsl
// @MaterialParameter
uniform vec4 u_baseColor;
```

### Notes
- Inline comments after the declaration are fine, but the metadata annotation itself must be a single-line `// @...` comment directly above the declaration.
- Block comments such as `/* @Sampler ... */` are not the supported format.
- If you omit `name`, the generator will try to infer the name from the declaration line.
- For engine-backed values, use `src` to point at one of the built-in providers such as `Renderer.SunDirection` or `Camera.ViewProjection`.

This is the format the build tools expect, so using it consistently keeps shader metadata accurate and makes the shader self-documenting for other authors.
